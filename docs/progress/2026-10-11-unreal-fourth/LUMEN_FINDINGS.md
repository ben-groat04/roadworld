# Black shadows and Lumen: findings (UE 5.8.3, RTX 4060, 11 Oct 2026)

Method: `screenshot_views.py` argument `diag[:cfg,...,view:<substr>]` applies console commands/hooks per configuration, waits 300-600 frames, shoots look_08 and look_02 (and 04/05 in some runs). Pixel numbers = mean linear luminance of the output PNG at fixed pixels (road (900,900), median shadow (1600,840) in look_08; slab (500,1000) and sunlit grass (900,1060) in look_02). Evidence images: `diag_evidence/`.

## VERIFIED
1. The black slabs are direct SUN shadows, not missing indirect light. `ShowFlag.DynamicShadows 0` removes them entirely (shadow pixel 0.0137 -> 0.0993 in look_08; slab 0.014 -> 0.131 in look_02). Cascaded shadow maps instead of virtual shadow maps: same shadow (0.0137 vs 0.0174). So not a VSM artefact.
2. The fill in the shadow is physically about right, the output is crushed. `ShowFlag.LightingOnlyOverride 1` shows the shade as blue-grey at 22% of sunlit (clear-sky shade/sun is about 20%). With `ShowFlag.Tonemapper 0` the shadow rises 3.3x (0.0137 -> 0.0412) while sunlit grass rises only 1.17x. Grass albedo is low (~0.08) and the filmic toe plus fixed EV100 14 maps the shade to near black. => hypothesis (iii) (exposure/tone mapping crushing a dim but correct value) is the dominant cause; (i) and (ii) are not.
3. Sky light is the only fill: `r.SkylightIntensityMultiplier 0` -> shadow exactly 0.000. Multiplier does not change the visible sky, only the fill (sky2: shadow 0.046, sky still saturated blue).
4. Not the cause (measured, no change beyond noise): `r.Lumen.DiffuseIndirect.Allow 0` (shadow 0.0196, slightly brighter), `r.DistanceFieldAO 0` (0.0158), the 40 km floor excluded from distance-field lighting (0.0165). NOTE: an early run that seemed to show DFAO responsible was contaminated by the previous config's sky multiplier (the real-time sky capture converges slowly); it was re-run and retracted.
5. Hardware ray-traced Lumen (`r.Lumen.HardwareRayTracing 1`, surface-cache hit lighting) makes the shade DARKER, not lighter: 0.0051 vs 0.0137 (with DFAO off 0.0050). `r.RayTracing.Geometry.ProceduralMeshes` is 1 by default and PMC does define ray-tracing geometry (engine source), so PMC meshes are in the ray-traced scene, but they have no Lumen surface cache/cards, so rays hitting them return dark. Excluding PMC from RT (`...ProceduralMeshes 0`) gives 0.0159 (about baseline). So with software Lumen the PMC meshes are simply invisible to Lumen; with HWRT they become black occluders.
6. HWRT with hit lighting (`r.Lumen.HardwareRayTracing.LightingMode 1`) CRASHED the GPU (D3D12 device removed, "Failed to create pipeline state ... 887a0005") while compiling the hit-lighting ray-tracing pipeline on this machine, in the one attempt made. Not retried. So hit lighting for PMC: not working here.
7. Frame time (slate tick mean, editor viewport, probably capped near 60 Hz so it hides cost): baseline 17-19 ms, HWRT 19-22 ms (first HWRT use stalled the editor for about 5 minutes compiling RT shaders). Real GPU cost NOT measured (see below).
8. Engine source (StaticMesh.cpp BuildFromMeshDescriptions): runtime/packaged builds only allow the fast build, which creates no distance field and no Lumen cards; only the editor `Build()` path does. So runtime `UStaticMesh` tiles cannot enter software Lumen in a shipped game.
9. The navy horizon band is the height fog applied to near-horizon SKY pixels: `ShowFlag.Fog 0` removes it; `fog_cutoff_distance` 30 km removes it (sky pixels exempt); fog max opacity/colour/density/aerial-perspective changes did not.

## NOT verified / assumed
- Lumen Scene / Surface Cache visualisation views: the console route (`ShowFlag.VisualizeLumen` + `r.Lumen.Visualize.ViewMode`) did not switch the editor viewport; I have no picture of which meshes are in the Lumen scene. Claims about PMC absence from software Lumen rest on engine source and on the HWRT/non-HWRT behaviour above.
- A runtime/editor-built `UStaticMesh` with distance fields and cards was NOT built or tested (time box). Source says the editor path generates them.
- Real GPU milliseconds (`stat gpu`): `screenshot_views.py gpuprof` was added but not run.
- Why a 4 m-wide median strip is in sun shadow beside a flat carriageway was not investigated (look_02 slabs are the 6 m deck shadows and are expected). Possible sim geometry (median lower than carriageway); someone should check heights.
- Sun direction: slabs appear on the camera side of look_02, i.e. shadows fall toward the camera; not checked against the intended SW sun.

## Fix applied (preference 2: sky fill + exposure, no Lumen change)
`SKY_INTENSITY` 3.0 -> 7.0, `EXPOSURE_BIAS_EV` -0.35 (shade about 3x brighter: shadow 0.0137 -> ~0.035-0.045; sky stays clear blue). Film toe change was rejected (it greys the sky). Cost: none measurable. Shadows now read dark green-grey, not black (`stage1_shadows_final/`).
Recommendation: keep PMC out of HWRT (`r.RayTracing.Geometry.ProceduralMeshes 0` if HWRT is ever enabled) and do not buy RMC Pro for this reason: it would not give PMC-style meshes Lumen cards either. A decision for the person is only needed if real bounce/occlusion under bridges becomes important (then editor-built static meshes for baked-ish content, or a custom card-less approach).
